# Contributing to INSPIRE

Thanks for your interest in INSPIRE. The project is maintained by a small core team. This document explains how to open an issue, how to pick up work, and what a pull request needs.

Please read it before opening an issue or a pull request. Contributions that don't follow it may be closed without review.

## The short version

1. Find or open an issue.
2. Wait until a maintainer **assigns it to you**.
3. Open one focused pull request that links that issue, with tests and green CI.


## Opening an issue

- **Search first**, including closed issues.
- **One problem per issue.**
- **Bug reports** must say what you did, what you expected, and what happened instead, plus the page URL or record ID and, for UI problems, your browser. If we can't reproduce it, we'll close it.
- **Feature requests** must describe the problem a real user has and who is affected, not only the solution you have in mind.
- **Issues must describe something real.** We close issues that are speculative ("this could be refactored", "consider migrating to X"), that were generated by a tool without the reporter checking them, or that were opened only to have something to work on.

Opening an issue does not mean it will be accepted or scheduled. A maintainer triages it first. Don't start work on an issue you opened until it has been accepted and assigned to you.

## Picking up an issue

- **Any open, unassigned issue can be requested**, but some are reserved for the core team, such as work that is already planned or touches production infrastructure. A maintainer will tell you when that's the case.
- **Ask, then wait to be assigned.** Comment on the issue saying you'd like to work on it and how you plan to do it. A comment does not claim the issue. It is yours only once a maintainer assigns you.
- **Don't assign yourself**, even if GitHub lets you. Maintainers handle assignment.
- **If someone else is assigned, pick another issue.**
- **Take one issue at a time** until your first pull request is merged.

Want to work on something that has no issue yet? Open one and ask first. Don't open the pull request first.

## Pull requests

### Title and description

Use the title format `<area>: <what changed>`, for example `ui: fix date filter on the conferences page`. The area is one of `backend`, `backoffice`, `workflows`, `ui`, `record-editor`, `e2e`, `renderer`, or `general` for changes that span several services.

In the description, explain what changed, why, and how you tested it.

## What we close without detailed review

- Pull requests without a linked issue assigned to the author (except the trivial fixes listed above)
- Pull requests for an issue assigned to someone else
- Pull requests that mix unrelated changes
- Pull requests with failing CI and no response from the author
- Bulk changes across the codebase: mass reformatting, typo sweeps across many files, or dependency bumps (Dependabot already handles these)

## AI-assisted contributions

You may use AI tools, but you are responsible for everything you submit:

- You have read and understood every line, and you can explain it in review.
- You ran the code and the tests yourself.
- You reproduced any bug you report yourself. A tool flagging it is not enough.

We close issues and pull requests that read as unreviewed tool output.

## Conduct

Be respectful and assume good faith. Maintainers may lock threads or block accounts that harass others or repeatedly ignore this policy.
